## 1. SQL Basics

SQL commands are grouped into 5 categories based on what they do.

| Category | Full Form | Commands |
|---|---|---|
| DDL | Data Definition Language | CREATE, ALTER, DROP, TRUNCATE, RENAME |
| DML | Data Manipulation Language | INSERT, UPDATE, DELETE |
| DQL | Data Query Language | SELECT |
| DCL | Data Control Language | GRANT, REVOKE |
| TCL | Transaction Control Language | COMMIT, ROLLBACK, SAVEPOINT |

### DDL
**What:** Commands that define or change the *structure* of database objects.
**Why:** Used whenever you create/modify a table or schema. DDL auto-commits — changes are permanent immediately.
**Syntax:**
```sql
CREATE TABLE table_name (col1 datatype, col2 datatype);
ALTER TABLE table_name ADD col3 datatype;
DROP TABLE table_name;
TRUNCATE TABLE table_name;
```
**Example:**
```sql
CREATE TABLE employees (
    emp_id   INT PRIMARY KEY,
    emp_name VARCHAR(50),
    salary   DECIMAL(10,2)
);
```
**Explanation:** Creates a new table `employees` with 3 columns and a primary key on `emp_id`. The structure now exists in the database, empty of data.

### DML
**What:** Commands that manipulate the *data* inside tables.
**Why:** Used to add, change, or remove rows. Can be rolled back (unlike DDL).
**Syntax:**
```sql
INSERT INTO table_name (col1, col2) VALUES (val1, val2);
UPDATE table_name SET col1 = val1 WHERE condition;
DELETE FROM table_name WHERE condition;
```
**Example:**
```sql
INSERT INTO employees VALUES (1, 'Arun', 50000);
UPDATE employees SET salary = 55000 WHERE emp_id = 1;
DELETE FROM employees WHERE emp_id = 1;
```
**Explanation:** First inserts a row, then updates that row's salary, then deletes it. Each of these can be undone with `ROLLBACK` if not yet committed.

### DQL
**What:** The single command used to *read* data.
**Why:** This is what you use 90% of the time — to fetch/report data.
**Syntax:**
```sql
SELECT col1, col2 FROM table_name WHERE condition;
```
**Example:**
```sql
SELECT emp_name, salary FROM employees WHERE salary > 40000;
```
**Explanation:** Returns names and salaries of employees earning more than 40,000.

### DCL
**What:** Commands that control access/permissions on database objects.
**Why:** Used by DBAs to secure data — who can read/write what.
**Syntax:**
```sql
GRANT SELECT, INSERT ON table_name TO user_name;
REVOKE INSERT ON table_name FROM user_name;
```
**Example:**
```sql
GRANT SELECT ON employees TO analyst_user;
```
**Explanation:** Gives `analyst_user` read-only access to the `employees` table.

### TCL
**What:** Commands that manage transactions — grouping DML statements so they succeed or fail together.
**Why:** Ensures data integrity (all-or-nothing changes), critical for banking/order systems.
**Syntax:**
```sql
BEGIN TRANSACTION;
SAVEPOINT sp1;
COMMIT;
ROLLBACK [TO sp1];
```
**Example:**
```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE acc_id = 1;
UPDATE accounts SET balance = balance + 500 WHERE acc_id = 2;
COMMIT;
```
**Explanation:** Both updates (money out of one account, into another) happen as a single atomic unit. If anything fails before `COMMIT`, you can `ROLLBACK` and neither update takes effect — preventing money from vanishing.

## 2. Database Objects

### TABLE
**What:** The core structure that stores data in rows and columns.
**Why:** Every piece of relational data lives in a table.
**Syntax:**
```sql
CREATE TABLE table_name (col1 datatype, ...);
```
**Example:**
```sql
CREATE TABLE departments (dept_id INT PRIMARY KEY, dept_name VARCHAR(30));
```
**Explanation:** A simple lookup table for department IDs and names.

### VIEW
**What:** A saved, virtual table defined by a SELECT query. Doesn't store data itself.
**Why:** Simplifies complex/repeated queries, adds a security layer (expose only certain columns), and improves readability.
**Syntax:**
```sql
CREATE VIEW view_name AS SELECT ... FROM ... WHERE ...;
```
**Example:**
```sql
CREATE VIEW high_earners AS
SELECT emp_name, salary FROM employees WHERE salary > 50000;

SELECT * FROM high_earners;
```
**Explanation:** `high_earners` looks like a table but is really just the stored query. Every time you `SELECT` from it, the underlying query re-runs live.

### MATERIALIZED VIEW
**What:** Like a view, but the result is physically stored and periodically refreshed.
**Why:** Used for performance — avoids re-running expensive aggregations every time; trades freshness for speed.
**Syntax:**
```sql
CREATE MATERIALIZED VIEW mv_name AS SELECT ...;
REFRESH MATERIALIZED VIEW mv_name;
```
**Example:**
```sql
CREATE MATERIALIZED VIEW monthly_sales AS
SELECT product_id, SUM(amount) AS total FROM sales GROUP BY product_id;
```
**Explanation:** `monthly_sales` stores actual precomputed totals on disk. Querying it is fast because no aggregation runs at query time — but data can go stale until refreshed.

### INDEX
**What:** A separate lookup structure that speeds up row retrieval on specific columns.
**Why:** Without an index, the database scans the whole table (full table scan) to find rows — slow on large tables.
**Syntax:**
```sql
CREATE INDEX idx_name ON table_name (col1);
```
**Example:**
```sql
CREATE INDEX idx_emp_salary ON employees (salary);
```
**Explanation:** Speeds up queries like `WHERE salary > 50000` because the engine can use the index tree instead of scanning every row.

### GTT (Global Temporary Table)
**What:** A table whose structure is permanent, but data is session-specific and auto-cleared.
**Why:** Useful for holding intermediate results during a session/transaction without affecting other users.
**Syntax:**
```sql
CREATE GLOBAL TEMPORARY TABLE gtt_name (col1 datatype) ON COMMIT DELETE ROWS;
```
**Example:**
```sql
CREATE GLOBAL TEMPORARY TABLE temp_calc (emp_id INT, bonus DECIMAL) ON COMMIT DELETE ROWS;
```
**Explanation:** Any rows inserted into `temp_calc` are visible only to your session and vanish automatically after `COMMIT`.

### EXTERNAL TABLE
**What:** A table definition that reads data from a file outside the database (e.g., CSV, S3) as if it were a normal table.
**Why:** Lets you query flat files directly without loading/importing them first — common in data lakes.
**Syntax:**
```sql
CREATE EXTERNAL TABLE ext_table_name (col1 datatype)
LOCATION 'path/to/file' FILE FORMAT csv;
```
**Example:**
```sql
CREATE EXTERNAL TABLE ext_sales (product_id INT, amount DECIMAL)
LOCATION '/data/sales.csv' FILE FORMAT csv;
```
**Explanation:** `ext_sales` doesn't copy data into the database — it reads directly from `sales.csv` on query.

## 3. Constraints

**What:** Rules enforced on columns to maintain data accuracy and integrity.
**Why:** Prevents bad data (duplicates, nulls, invalid foreign references) from entering the database.

### PRIMARY KEY
**Syntax:** `col datatype PRIMARY KEY` or `CONSTRAINT pk_name PRIMARY KEY (col)`
**Example:**
```sql
CREATE TABLE students (student_id INT PRIMARY KEY, name VARCHAR(30));
```
**Explanation:** `student_id` must be unique and cannot be NULL — uniquely identifies each row.

### UNIQUE
**Syntax:** `col datatype UNIQUE`
**Example:**
```sql
CREATE TABLE users (email VARCHAR(50) UNIQUE);
```
**Explanation:** No two rows can have the same email, but unlike PRIMARY KEY, NULLs are allowed (and multiple NULLs, in most DBs).

### NOT NULL
**Syntax:** `col datatype NOT NULL`
**Example:**
```sql
CREATE TABLE orders (order_id INT, order_date DATE NOT NULL);
```
**Explanation:** Every row must have an `order_date` — inserting NULL here fails.

### CHECK
**Syntax:** `CHECK (condition)`
**Example:**
```sql
CREATE TABLE employees (salary DECIMAL CHECK (salary > 0));
```
**Explanation:** Rejects any row where salary is 0 or negative.

### FOREIGN KEY
**Syntax:** `FOREIGN KEY (col) REFERENCES other_table(col)`
**Example:**
```sql
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    cust_id  INT,
    FOREIGN KEY (cust_id) REFERENCES customers(cust_id)
);
```
**Explanation:** Every `cust_id` in `orders` must already exist in `customers` — enforces referential integrity between related tables.

## 4. Data Types

**What:** Defines the kind of value a column can hold.
**Why:** Ensures correct storage, validation, and enables type-specific operations (date math, numeric aggregation, etc.).

| Category | Examples | Use For |
|---|---|---|
| Numeric | INT, DECIMAL(p,s), FLOAT | IDs, money, measurements |
| Character | CHAR(n), VARCHAR(n), TEXT | fixed/variable-length text |
| Date/Time | DATE, TIME, TIMESTAMP | dates, timestamps |
| Boolean | BOOLEAN | true/false flags |
| Binary | BLOB, BYTEA | images, files |

**Example:**
```sql
CREATE TABLE products (
    product_id INT,
    name       VARCHAR(50),
    price      DECIMAL(8,2),
    in_stock   BOOLEAN,
    added_on   DATE
);
```
**Explanation:** `DECIMAL(8,2)` stores up to 8 digits total with 2 after the decimal — ideal for money since it avoids floating-point rounding errors.

## 5. Basic SQL

### SELECT / FROM
**What:** Chooses which columns and table to read data from.
**Why:** The starting point of every query.
**Syntax:** `SELECT col1, col2 FROM table_name;`
**Example:**
```sql
SELECT emp_name, salary FROM employees;
```
**Explanation:** Returns two columns for every row in `employees`.

### WHERE
**What:** Filters rows *before* grouping, based on a condition.
**Why:** Restrict results to only relevant rows.
**Syntax:** `SELECT * FROM table WHERE condition;`
**Example:**
```sql
SELECT * FROM employees WHERE salary > 50000 AND dept = 'IT';
```
**Explanation:** Only returns IT employees earning above 50,000.

### DISTINCT
**What:** Removes duplicate rows from the result.
**Why:** Used to list unique values.
**Syntax:** `SELECT DISTINCT col FROM table;`
**Example:**
```sql
SELECT DISTINCT dept FROM employees;
```
**Explanation:** Returns each department name once, even if many employees share it.

### GROUP BY
**What:** Groups rows sharing the same value(s) so aggregate functions can be applied per group.
**Why:** Used for summaries — e.g., total salary per department.
**Syntax:** `SELECT col, AGG(col2) FROM table GROUP BY col;`
**Example:**
```sql
SELECT dept, SUM(salary) FROM employees GROUP BY dept;
```
**Explanation:** One row per department, showing the total salary within each.

### HAVING
**What:** Filters *groups* after `GROUP BY` (unlike `WHERE`, which filters rows before grouping).
**Why:** Needed when your filter condition involves an aggregate.
**Syntax:** `... GROUP BY col HAVING agg_condition;`
**Example:**
```sql
SELECT dept, SUM(salary) AS total
FROM employees
GROUP BY dept
HAVING SUM(salary) > 100000;
```
**Explanation:** Only shows departments whose total salary exceeds 100,000. You can't write `WHERE SUM(salary) > 100000` because `WHERE` runs before aggregation exists.

### ORDER BY
**What:** Sorts the final result set.
**Why:** Presentation — ranking, top-N, alphabetical listing.
**Syntax:** `... ORDER BY col [ASC|DESC];`
**Example:**
```sql
SELECT emp_name, salary FROM employees ORDER BY salary DESC;
```
**Explanation:** Lists employees from highest to lowest salary.

> **Logical order of execution:** `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY` — a very common interview question.

## 6. Operators

### Relational
**What:** Compare two values: `=, !=, <>, >, <, >=, <=`
**Why:** Basic filtering condition building.
**Example:** `SELECT * FROM employees WHERE salary >= 50000;`
**Explanation:** Returns rows where salary is 50,000 or more.

### Logical
**What:** Combine multiple conditions: `AND, OR, NOT`
**Why:** Build complex filters.
**Example:** `SELECT * FROM employees WHERE dept = 'IT' AND NOT salary < 30000;`
**Explanation:** IT employees with salary NOT less than 30,000 (i.e., ≥ 30,000).

### LIKE / IN / BETWEEN / NULL
**What:**
- `LIKE` — pattern matching text (`%` = any chars, `_` = one char)
- `IN` — matches any value in a list
- `BETWEEN` — matches a range (inclusive)
- `IS NULL` / `IS NOT NULL` — checks for missing values

**Why:** These cover the most common real-world filter patterns beyond simple equality.
**Syntax + Example:**
```sql
SELECT * FROM employees WHERE emp_name LIKE 'A%';         -- starts with A
SELECT * FROM employees WHERE dept IN ('IT','HR');        -- IT or HR
SELECT * FROM employees WHERE salary BETWEEN 30000 AND 60000;
SELECT * FROM employees WHERE manager_id IS NULL;          -- no manager
```
**Explanation:** `LIKE 'A%'` finds names starting with A. `IN` avoids chaining many `OR`s. `BETWEEN` is inclusive of both boundaries. `IS NULL` must be used instead of `= NULL` because NULL is "unknown," not comparable with `=`.

## 7. Functions

### Number Functions
**What:** Operate on numeric values — `ROUND, CEIL, FLOOR, ABS, MOD, POWER`
**Why:** Formatting and math on numeric columns.
**Example:**
```sql
SELECT ROUND(45.678, 2), CEIL(45.2), FLOOR(45.8), MOD(10,3);
```
**Explanation:** Returns `45.68`, `46`, `45`, `1` respectively — rounding, ceiling, flooring, and remainder.

### Character Functions
**What:** Operate on text — `UPPER, LOWER, SUBSTRING, TRIM, CONCAT, LENGTH, REPLACE`
**Why:** Clean, format, or combine string data.
**Example:**
```sql
SELECT CONCAT(UPPER(first_name), ' ', LOWER(last_name)) AS full_name
FROM employees;
```
**Explanation:** Builds a name like `"ARUN kumar"` — first name uppercase, last name lowercase, joined with a space.

### Date Functions
**What:** Operate on dates — `SYSDATE/CURRENT_DATE, DATEADD, DATEDIFF, EXTRACT, TO_DATE`
**Why:** Date math is one of the most common real-world SQL needs.
**Example:**
```sql
SELECT emp_name, DATEDIFF(CURRENT_DATE, hire_date) AS days_employed
FROM employees;
```
**Explanation:** Calculates how many days each employee has worked, using today's date minus hire date.

### Conversion Functions
**What:** Convert between data types — `CAST, CONVERT, TO_CHAR, TO_NUMBER, TO_DATE`
**Why:** You often need to compare/combine values of different types.
**Example:**
```sql
SELECT CAST(salary AS VARCHAR) || ' USD' AS salary_text FROM employees;
```
**Explanation:** Converts numeric salary to text so it can be concatenated with the string `' USD'`.

### NULL / General Functions
**What:** Handle NULLs — `COALESCE, NULLIF, ISNULL/NVL`
**Why:** NULLs break math and comparisons unless handled explicitly.
**Example:**
```sql
SELECT emp_name, COALESCE(bonus, 0) AS bonus FROM employees;
```
**Explanation:** If `bonus` is NULL, shows `0` instead — avoids NULLs propagating into calculations like `salary + bonus`.

## 8. Aggregations

**What:** Functions that compute a single summary value from multiple rows.
**Why:** Core to reporting/analytics — totals, averages, counts.

| Function | Purpose |
|---|---|
| COUNT | number of rows |
| SUM | total of a numeric column |
| AVG | average value |
| MIN | smallest value |
| MAX | largest value |

**Syntax:** `SELECT AGG_FUNC(col) FROM table [GROUP BY col];`
**Example:**
```sql
SELECT dept,
       COUNT(*)      AS emp_count,
       SUM(salary)    AS total_salary,
       AVG(salary)    AS avg_salary,
       MIN(salary)    AS min_salary,
       MAX(salary)    AS max_salary
FROM employees
GROUP BY dept;
```
**Explanation:** For each department, gives headcount, total pay, average pay, and pay range in one query. `COUNT(*)` counts all rows including NULLs; `COUNT(col)` skips NULLs in that column.

## 9. Joins

**What:** Combine rows from two or more tables based on a related column.
**Why:** Relational data is normalized across tables — joins let you bring it back together for querying.

Sample tables used below:
`employees(emp_id, emp_name, dept_id)` and `departments(dept_id, dept_name)`

### INNER JOIN
**Syntax:** `SELECT ... FROM A INNER JOIN B ON A.col = B.col;`
**Example:**
```sql
SELECT e.emp_name, d.dept_name
FROM employees e
INNER JOIN departments d ON e.dept_id = d.dept_id;
```
**Explanation:** Returns only employees who have a matching department — rows with no match on either side are excluded.

### LEFT JOIN
**Example:**
```sql
SELECT e.emp_name, d.dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;
```
**Explanation:** Returns all employees, even those with no matching department (dept_name shows as NULL).

### RIGHT JOIN
**Example:**
```sql
SELECT e.emp_name, d.dept_name
FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.dept_id;
```
**Explanation:** Returns all departments, even ones with no employees (emp_name shows as NULL).

### FULL JOIN
**Example:**
```sql
SELECT e.emp_name, d.dept_name
FROM employees e
FULL JOIN departments d ON e.dept_id = d.dept_id;
```
**Explanation:** Returns everything — matched rows, unmatched employees, and unmatched departments.

### CROSS JOIN
**Example:**
```sql
SELECT e.emp_name, d.dept_name FROM employees e CROSS JOIN departments d;
```
**Explanation:** Produces every possible combination (Cartesian product) — if 5 employees and 3 departments, returns 15 rows. Rarely used directly except for generating combinations.

### SELF JOIN
**Example:**
```sql
SELECT e1.emp_name AS employee, e2.emp_name AS manager
FROM employees e1
JOIN employees e2 ON e1.manager_id = e2.emp_id;
```
**Explanation:** Joins the `employees` table to itself to resolve each employee's manager name from the same table.

### SEMI JOIN
**What:** Returns rows from A that have a match in B, **without** duplicating A's rows or pulling B's columns. Implemented via `IN`/`EXISTS`, not a JOIN keyword in most SQL dialects.
**Example:**
```sql
SELECT * FROM employees e
WHERE EXISTS (SELECT 1 FROM departments d WHERE d.dept_id = e.dept_id);
```
**Explanation:** Returns employee rows whose department exists — but each employee appears only once, even if theoretically matched multiple times.

### ANTI JOIN
**What:** Returns rows from A that have **no** match in B.
**Example:**
```sql
SELECT * FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM departments d WHERE d.dept_id = e.dept_id);
```
**Explanation:** Finds employees whose `dept_id` doesn't exist in `departments` — useful for finding orphaned/broken references.

## 10. Set Operators

**What:** Combine the results of two or more `SELECT` queries (same number/type of columns).
**Why:** Merge or compare result sets from different queries.

### UNION
**Syntax:** `query1 UNION query2;`
**Example:**
```sql
SELECT emp_name FROM employees_2023
UNION
SELECT emp_name FROM employees_2024;
```
**Explanation:** Combines names from both years, automatically removing duplicates.

### UNION ALL
**Example:**
```sql
SELECT emp_name FROM employees_2023
UNION ALL
SELECT emp_name FROM employees_2024;
```
**Explanation:** Same as UNION but keeps duplicates — faster since no dedup step is needed.

### INTERSECT
**Example:**
```sql
SELECT emp_name FROM employees_2023
INTERSECT
SELECT emp_name FROM employees_2024;
```
**Explanation:** Returns only names present in **both** years.

### MINUS (a.k.a. EXCEPT)
**Example:**
```sql
SELECT emp_name FROM employees_2023
MINUS
SELECT emp_name FROM employees_2024;
```
**Explanation:** Returns names in `employees_2023` that are **not** in `employees_2024` — e.g., employees who left.

## 11. Subqueries

**What:** A query nested inside another query.
**Why:** Lets you break a problem into steps — compute something first, then use it in the outer query.

### Scalar Subquery
**What:** Returns a single value.
**Example:**
```sql
SELECT emp_name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);
```
**Explanation:** The inner query computes one number (average salary); the outer query compares each employee against it.

### Inline View
**What:** A subquery used in the `FROM` clause, treated as a temporary table.
**Example:**
```sql
SELECT dept, avg_sal
FROM (SELECT dept, AVG(salary) AS avg_sal FROM employees GROUP BY dept) t
WHERE avg_sal > 50000;
```
**Explanation:** The inner query pre-aggregates by department; the outer query filters on that aggregated result.

### Nested Subquery
**What:** A subquery inside a `WHERE`/`IN` clause, evaluated independently of the outer query.
**Example:**
```sql
SELECT emp_name FROM employees
WHERE dept_id IN (SELECT dept_id FROM departments WHERE location = 'Chennai');
```
**Explanation:** First finds all Chennai department IDs, then finds employees in those departments.

### Correlated Subquery
**What:** A subquery that references a column from the outer query — re-executes for each outer row.
**Example:**
```sql
SELECT e.emp_name, e.salary
FROM employees e
WHERE e.salary > (
    SELECT AVG(salary) FROM employees WHERE dept_id = e.dept_id
);
```
**Explanation:** For each employee, compares their salary to the average salary *of their own department* — the inner query depends on `e.dept_id` from the outer row.

### Non-correlated Subquery
**What:** A subquery that runs independently, once, regardless of the outer query.
**Example:** (same as the Scalar Subquery example above)
**Explanation:** The inner `SELECT AVG(salary) FROM employees` computes once and is reused for every outer row — no dependency on the outer table.

## 12. CTE

### WITH (Common Table Expression)
**What:** A named, temporary result set defined at the top of a query using `WITH`.
**Why:** Improves readability over nested subqueries; lets you reuse the same intermediate result multiple times.
**Syntax:**
```sql
WITH cte_name AS (
    SELECT ...
)
SELECT * FROM cte_name;
```
**Example:**
```sql
WITH dept_avg AS (
    SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id
)
SELECT e.emp_name, d.avg_sal
FROM employees e
JOIN dept_avg d ON e.dept_id = d.dept_id
WHERE e.salary > d.avg_sal;
```
**Explanation:** `dept_avg` is computed once and named, then joined back to `employees` — cleaner than writing the aggregation as a nested subquery.

### Recursive CTE
**What:** A CTE that references itself to process hierarchical or sequential data.
**Why:** Used for org charts, category trees, or generating number/date sequences.
**Syntax:**
```sql
WITH RECURSIVE cte_name AS (
    -- anchor member
    SELECT ...
    UNION ALL
    -- recursive member
    SELECT ... FROM table JOIN cte_name ON ...
)
SELECT * FROM cte_name;
```
**Example:**
```sql
WITH RECURSIVE emp_hierarchy AS (
    SELECT emp_id, emp_name, manager_id, 1 AS level
    FROM employees WHERE manager_id IS NULL      -- anchor: top boss

    UNION ALL

    SELECT e.emp_id, e.emp_name, e.manager_id, h.level + 1
    FROM employees e
    JOIN emp_hierarchy h ON e.manager_id = h.emp_id  -- recursive step
)
SELECT * FROM emp_hierarchy;
```
**Explanation:** The anchor picks the top-level manager (no manager). The recursive part repeatedly joins the next level of employees to the previous result, building the full reporting chain with a `level` counter.

## 13. Analytical Functions

**What:** Window functions that compute a value across a set of rows ("window") related to the current row, **without** collapsing rows like `GROUP BY` does.
**Why:** Essential for ranking, running totals, and row-to-row comparisons while keeping all detail rows visible.
**General Syntax:**
```sql
FUNC() OVER (PARTITION BY col ORDER BY col)
```

### ROW_NUMBER
**Example:**
```sql
SELECT emp_name, dept_id, salary,
       ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
FROM employees;
```
**Explanation:** Assigns a unique, sequential number to each employee within their department, ordered by salary — highest paid gets `rn = 1`. No ties — always unique.

### RANK
**Example:**
```sql
SELECT emp_name, salary,
       RANK() OVER (ORDER BY salary DESC) AS rnk
FROM employees;
```
**Explanation:** Same salary → same rank, but the next rank **skips** numbers (e.g., 1,1,3).

### DENSE_RANK
**Example:**
```sql
SELECT emp_name, salary,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS drnk
FROM employees;
```
**Explanation:** Same as RANK, but **no gaps** in ranking (e.g., 1,1,2).

### LAG
**Example:**
```sql
SELECT emp_name, salary,
       LAG(salary, 1) OVER (ORDER BY hire_date) AS prev_salary
FROM employees;
```
**Explanation:** Shows the salary of the **previous row** (by hire date) alongside the current row — useful for period-over-period comparison.

### LEAD
**Example:**
```sql
SELECT emp_name, salary,
       LEAD(salary, 1) OVER (ORDER BY hire_date) AS next_salary
FROM employees;
```
**Explanation:** Shows the salary of the **next row** — opposite of LAG.

### NTILE
**Example:**
```sql
SELECT emp_name, salary,
       NTILE(4) OVER (ORDER BY salary DESC) AS quartile
FROM employees;
```
**Explanation:** Splits employees into 4 equal-sized buckets by salary rank — used for quartile/percentile analysis.

### Running Total
**Example:**
```sql
SELECT order_date, amount,
       SUM(amount) OVER (ORDER BY order_date) AS running_total
FROM orders;
```
**Explanation:** For each row, sums all `amount` values from the start up to the current row — a cumulative total over time.

### Window Aggregates
**Example:**
```sql
SELECT emp_name, dept_id, salary,
       AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
FROM employees;
```
**Explanation:** Shows each employee's salary next to their department's average — unlike `GROUP BY`, every individual row is still visible.

## 14. CASE

**What:** SQL's if/else expression — evaluates conditions and returns a value.
**Why:** Used for conditional labeling, bucketing, and pivot-style transformations.
**Syntax:**
```sql
CASE
    WHEN condition1 THEN result1
    WHEN condition2 THEN result2
    ELSE default_result
END
```
**Example:**
```sql
SELECT emp_name, salary,
    CASE
        WHEN salary >= 80000 THEN 'High'
        WHEN salary >= 50000 THEN 'Medium'
        ELSE 'Low'
    END AS salary_band
FROM employees;
```
**Explanation:** Labels each employee's salary as High/Medium/Low based on thresholds — conditions are checked top to bottom, first match wins.

## 15. Advanced GROUP BY

**What:** Extensions to `GROUP BY` that compute multiple levels of subtotals in a single query.
**Why:** Avoids writing multiple `UNION`-ed queries to get subtotals + grand totals.

### ROLLUP
**Syntax:** `GROUP BY ROLLUP (col1, col2)`
**Example:**
```sql
SELECT dept_id, job_title, SUM(salary)
FROM employees
GROUP BY ROLLUP (dept_id, job_title);
```
**Explanation:** Produces normal group totals (by dept+job), then subtotals per department, then one grand total — hierarchical rollup from detailed to overall.

### CUBE
**Syntax:** `GROUP BY CUBE (col1, col2)`
**Example:**
```sql
SELECT dept_id, job_title, SUM(salary)
FROM employees
GROUP BY CUBE (dept_id, job_title);
```
**Explanation:** Produces subtotals for **every possible combination** — by dept, by job, by dept+job, and grand total. More exhaustive than ROLLUP.

### GROUPING SETS
**Syntax:** `GROUP BY GROUPING SETS ((col1), (col2), ())`
**Example:**
```sql
SELECT dept_id, job_title, SUM(salary)
FROM employees
GROUP BY GROUPING SETS ((dept_id), (job_title), ());
```
**Explanation:** Lets you specify **exactly** which grouping combinations you want (here: by dept alone, by job alone, and grand total) — more control than CUBE/ROLLUP.

## 16. MERGE

**What:** Combines `INSERT`, `UPDATE`, and `DELETE` into a single statement based on whether a match is found ("upsert").
**Why:** Common in ETL/data-sync jobs — update existing records, insert new ones, in one pass instead of separate statements.
**Syntax:**
```sql
MERGE INTO target t
USING source s ON (t.id = s.id)
WHEN MATCHED THEN UPDATE SET t.col = s.col
WHEN NOT MATCHED THEN INSERT (col1, col2) VALUES (s.col1, s.col2);
```
**Example:**
```sql
MERGE INTO employees e
USING staging_employees s
ON (e.emp_id = s.emp_id)
WHEN MATCHED THEN
    UPDATE SET e.salary = s.salary
WHEN NOT MATCHED THEN
    INSERT (emp_id, emp_name, salary) VALUES (s.emp_id, s.emp_name, s.salary);
```
**Explanation:** For every row in `staging_employees`, if the `emp_id` already exists in `employees`, update the salary; otherwise insert it as a brand-new employee — all in one statement.

## 17. Indexes

**What:** Data structures that speed up data retrieval at the cost of extra storage and slower writes.
**Why:** Query performance — the single biggest lever for making `SELECT`s fast on large tables.

### Unique Index
**Example:** `CREATE UNIQUE INDEX idx_email ON users(email);`
**Explanation:** Speeds up lookups by email **and** enforces no duplicate emails.

### Non-unique Index
**Example:** `CREATE INDEX idx_dept ON employees(dept_id);`
**Explanation:** Speeds up filtering/joining on `dept_id`; duplicates are allowed.

### B-tree Index
**What:** The default index type — a balanced tree structure good for equality and range queries (`=, <, >, BETWEEN`).
**Explanation:** Used automatically by most `CREATE INDEX` statements; ideal for high-cardinality columns like IDs.

### Bitmap Index
**What:** Uses bitmaps to represent value presence — efficient for low-cardinality columns (few distinct values, e.g., gender, status).
**Explanation:** Great for `WHERE status = 'Active'` on data warehouses; not great for frequently updated columns (locking overhead).

### Function-based Index
**Example:** `CREATE INDEX idx_upper_name ON employees (UPPER(emp_name));`
**Explanation:** Indexes the *result of an expression* — speeds up queries like `WHERE UPPER(emp_name) = 'ARUN'`, which a normal index on `emp_name` couldn't accelerate.

### Composite Index
**Example:** `CREATE INDEX idx_dept_salary ON employees (dept_id, salary);`
**Explanation:** Indexes multiple columns together — most effective when queries filter/sort on the leading column(s) in the same order (`dept_id` first, then `salary`).

## 18. Query Optimization

**What:** The practice of writing/tuning SQL so the database engine executes it as efficiently as possible.
**Why:** Poorly written queries can take minutes instead of milliseconds on large datasets.

### EXPLAIN PLAN
**What:** Shows *how* the database intends to execute a query — which indexes it will use, join order, scan type.
**Syntax:** `EXPLAIN SELECT ...;`
**Example:**
```sql
EXPLAIN SELECT * FROM employees WHERE salary > 50000;
```
**Explanation:** Returns a plan showing whether the engine will do an index scan or a full table scan for this query — the first thing to check when a query is slow.

### Full Table Scan
**What:** The engine reads every row in the table to find matches.
**Why it matters:** Slow on large tables; happens when there's no usable index, or the query forces one (e.g., function on an indexed column without a function-based index).
**Example:** `SELECT * FROM employees WHERE UPPER(emp_name) = 'ARUN';` (with no function-based index) → full scan.

### Index Scan
**What:** The engine uses an index to jump directly to matching rows instead of scanning everything.
**Why it matters:** Much faster for selective conditions (returning a small % of rows).
**Example:** `SELECT * FROM employees WHERE emp_id = 101;` with a primary key index → fast index scan.

### Execution Plan
**What:** The full step-by-step strategy the optimizer picks: join order, join algorithm (nested loop/hash/merge join), filter order, and access paths.
**Why it matters:** Reading it tells you exactly where the time is going — e.g., a large table being scanned before a filter that should've run first.
**Tip for interviews:** Common fixes — add an index on filter/join columns, avoid `SELECT *`, avoid functions on indexed columns in `WHERE`, filter early, and prefer `EXISTS` over `IN` for large subqueries.

## 19. SQL Problem Solving

Classic interview patterns — these come up constantly.

### Duplicates
**Find duplicates:**
```sql
SELECT emp_name, COUNT(*)
FROM employees
GROUP BY emp_name
HAVING COUNT(*) > 1;
```
**Explanation:** Groups by name; `HAVING COUNT(*) > 1` keeps only names appearing more than once.

**Delete duplicates (keep lowest emp_id):**
```sql
DELETE FROM employees
WHERE emp_id NOT IN (
    SELECT MIN(emp_id) FROM employees GROUP BY emp_name
);
```
**Explanation:** For each duplicated name, keeps only the row with the smallest `emp_id` and deletes the rest.

### Nth Highest
```sql
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET (N-1);
```
**Or with DENSE_RANK:**
```sql
SELECT salary FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees
) t
WHERE rnk = N;
```
**Explanation:** `DENSE_RANK` correctly handles ties (e.g., two people with the highest salary both count as rank 1), unlike `LIMIT/OFFSET` which just skips rows positionally.

### Top N per Group
```sql
SELECT * FROM (
    SELECT emp_name, dept_id, salary,
           ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
    FROM employees
) t
WHERE rn <= 3;
```
**Explanation:** Ranks employees within each department by salary, then keeps only the top 3 per department.

### Missing Records
```sql
SELECT c.cust_id, c.cust_name
FROM customers c
LEFT JOIN orders o ON c.cust_id = o.cust_id
WHERE o.cust_id IS NULL;
```
**Explanation:** Finds customers who have **never placed an order** — LEFT JOIN keeps all customers, and filtering on `o.cust_id IS NULL` isolates the unmatched ones.

### Gaps (Missing Sequence Numbers)
```sql
SELECT (t1.id + 1) AS gap_start
FROM sequence_table t1
WHERE NOT EXISTS (SELECT 1 FROM sequence_table t2 WHERE t2.id = t1.id + 1)
AND t1.id < (SELECT MAX(id) FROM sequence_table);
```
**Explanation:** For each id, checks whether `id + 1` exists; if not, that's a gap in the sequence.

### Running Totals
```sql
SELECT order_date, amount,
       SUM(amount) OVER (ORDER BY order_date) AS running_total
FROM orders;
```
**Explanation:** (Same window function as Section 13) — cumulative sum ordered by date.

### Latest Record (per group)
```sql
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY cust_id ORDER BY order_date DESC) AS rn
    FROM orders
) t
WHERE rn = 1;
```
**Explanation:** For each customer, keeps only their single most recent order.

### Date Problems
**Employees hired in the last 30 days:**
```sql
SELECT emp_name FROM employees
WHERE hire_date >= CURRENT_DATE - INTERVAL '30 days';
```
**Month-over-month growth:**
```sql
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS mom_change
FROM monthly_revenue;
```
**Explanation:** First filters recent hires using date arithmetic. Second uses `LAG` to compare each month's revenue to the previous month.

### ETL-style Problems
**Deduplicate + load latest snapshot (typical staging → target pattern):**
```sql
MERGE INTO target_table t
USING (
    SELECT * FROM (
        SELECT *, ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC) AS rn
        FROM staging_table
    ) s WHERE rn = 1
) src
ON (t.id = src.id)
WHEN MATCHED THEN UPDATE SET t.value = src.value
WHEN NOT MATCHED THEN INSERT (id, value) VALUES (src.id, src.value);
```
**Explanation:** A classic ETL pattern — first dedupe the staging table to the latest record per `id` using `ROW_NUMBER`, then `MERGE` that clean result into the target table (update if exists, insert if new).

## Quick Reference: Order of Execution
```
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET
```
Knowing this order explains *why* you can't use a column alias in `WHERE` but can in `ORDER BY`, and why `HAVING` (not `WHERE`) is needed to filter on aggregates.
